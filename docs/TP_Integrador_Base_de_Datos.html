1Presentación del proyecto

1.1 Tema y objetivos

El presente trabajo integra los contenidos de las Unidades I a IV de Base de Datos I en el diseño y la implementación de un sistema de gestión para una veterinaria. El dominio cubre la administración de propietarios, mascotas, profesionales, consultas, diagnósticos, tratamientos, vacunaciones, cirugías e internaciones, con trazabilidad del historial clínico de cada paciente.

El objetivo general es diseñar, normalizar e implementar una base de datos relacional en MySQL que soporte la operación de la veterinaria, junto con una capa de acceso programático en Python mediante el ORM peewee, aplicando DDL, DCL, DML, transacciones, vistas y control de permisos por rol.

Los objetivos específicos son:

  • Modelar el dominio con notación Chen y con notación pata de gallo.
  • Normalizar el esquema hasta la Tercera Forma Normal (3FN).
  • Implementar el DDL con integridad referencial, restricciones CHECK, índices y triggers.
  • Poblar la base con datos coherentes y reproducibles.
  • Definir vistas de consulta y usuarios con permisos según el principio de mínimo privilegio.
  • Implementar un CRUD en Python sobre dos tablas relacionadas, con transacciones atómicas.
  • Documentar las decisiones de diseño y versionar todos los artefactos en GitHub.

2.1 Justificación de las decisiones

MySQL es el motor requerido por la cátedra y ofrece las garantías necesarias para el dominio: transacciones ACID, claves foráneas, restricciones CHECK, vistas, triggers y un sistema de privilegios granular. El motor InnoDB permite además definir reglas de borrado diferenciadas (RESTRICT y CASCADE) según la naturaleza del dato.

Python con peewee permite construir un CRUD conciso sin perder control sobre el SQL generado. peewee ofrece db.atomic() para agrupar operaciones en una transacción, lo que resulta ideal para el alta y la baja coordinada de propietario y mascota. PyMySQL es un driver puro Python, sin dependencias nativas, y cryptography es necesario para autenticarse contra MySQL 8.0 o superior cuando el usuario utiliza el plugin caching_sha2_password.

Graphviz se utilizó para generar los diagramas desde definiciones textuales, de modo que cualquier cambio en el modelo pueda reflejarse regenerando la imagen. La documentación se maquetó en HTML y se imprimió a PDF con Edge en modo headless, lo que permite mantener el documento dentro del mismo repositorio y repetir la compilación cuando sea necesario.

La relación 1:1 entre consulta y diagnostico se implementa con una clave foránea que además es única (uq_diagnostico_consulta). De este modo, una consulta no puede tener dos diagnósticos, pero puede no tener ninguno. Los tratamientos, en cambio, se mantienen en una tabla separada porque una consulta puede indicar varios y porque cada uno tiene atributos propios (medicamento, posología y duración).

Las reglas de borrado siguen un criterio clínico: los datos que forman parte de la historia del paciente no se eliminan en cascada (RESTRICT), mientras que el diagnóstico y los tratamientos son dependientes de la consulta y se eliminan con ella (CASCADE). Así se evita dejar registros huérfanos y se protege la trazabilidad.

3.5 Normalización

El esquema se normalizó hasta la Tercera Forma Normal. A continuación se justifica cada etapa con ejemplos concretos del dominio.

Primera Forma Normal (1FN)

Todos los atributos son atómicos y no existen grupos repetidos. Un propietario tiene un solo teléfono en la columna telefono; si en el futuro se necesitan varios, corresponde una tabla de teléfonos y no una lista separada por comas. Del mismo modo, los tratamientos de una consulta no se guardan como texto en consulta, sino como filas independientes en tratamiento.

Segunda Forma Normal (2FN)

Todos los atributos que no forman parte de la clave dependen de la clave completa. Como todas las tablas utilizan una clave primaria simple y sustituta, la 2FN se cumple por construcción. En raza, la unicidad compuesta (id_especie, nombre_raza) impide repetir la misma raza dentro de una especie, pero nombre_raza depende funcionalmente de id_raza.

Tercera Forma Normal (3FN)

No existen dependencias transitivas. El caso más importante es la especie de la mascota: en una versión previa, mascota contenía id_raza e id_especie. Como la especie se deduce de la raza, mantener ambas columnas generaba una dependencia transitiva (id_mascota → id_raza → id_especie) y el riesgo de inconsistencias. Se eliminó id_especie de mascota y la especie se obtiene mediante mascota → raza → especie.

El mismo criterio se aplicó a los datos del propietario (no se repiten en mascota), a los datos del veterinario (no se repiten en consulta) y a los tratamientos (no se almacenan como una lista dentro de la consulta). La edad de la mascota es un dato derivado: se calcula en la vista v_ficha_mascota con TIMESTAMPDIFF y no se almacena.

La validación de la fecha de nacimiento se resolvió con triggers, porque MySQL no permite CURDATE() en una restricción CHECK. El trigger se dispara antes de insertar o actualizar y rechaza la operación con un mensaje claro.

Listado 3. Trigger de validación de la fecha de nacimiento.
DELIMITER $$

CREATE TRIGGER trg_mascota_fecha_nac_bi
BEFORE INSERT ON mascota
FOR EACH ROW
BEGIN
    IF NEW.fecha_nacimiento > CURDATE() THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'La fecha de nacimiento no puede ser futura';
    END IF;
END$$

DELIMITER ;

5.5 Consultas destacadas

Además del CRUD, el script incluye consultas que ejercitan los contenidos de la materia. La primera es un JOIN de cuatro tablas con LEFT JOIN para incluir consultas sin diagnóstico.

Listado 7. JOIN de cuatro tablas: historial de una mascota.
SELECT
    m.nombre                    AS mascota,
    c.fecha,
    c.motivo,
    d.descripcion               AS diagnostico,
    CONCAT(v.nombre, ' ', v.apellido) AS veterinario
FROM mascota m
INNER JOIN consulta c     ON c.id_mascota = m.id_mascota
INNER JOIN veterinario v  ON v.id_veterinario = c.id_veterinario
LEFT JOIN diagnostico d   ON d.id_consulta = c.id_consulta
WHERE m.nombre = 'Firulais'
ORDER BY c.fecha;

La segunda agrupa por veterinario y filtra con HAVING los que tienen dos o más consultas. Se incluyen las columnas de agrupación en el GROUP BY para cumplir con ONLY_FULL_GROUP_BY.

Listado 8. GROUP BY con HAVING.
SELECT
    CONCAT(v.nombre, ' ', v.apellido) AS veterinario,
    v.especialidad,
    COUNT(c.id_consulta)              AS total_consultas
FROM veterinario v
LEFT JOIN consulta c ON c.id_veterinario = v.id_veterinario
GROUP BY v.id_veterinario, v.nombre, v.apellido, v.especialidad
HAVING COUNT(c.id_consulta) >= 2
ORDER BY total_consultas DESC;

La tercera utiliza una función de ventana para clasificar a los veterinarios, incluyendo a quienes no tienen consultas (LEFT JOIN). El resultado real fue: Ana Paredes 4 consultas (puesto 1), Raúl Benítez 3 (puesto 2), Julia Molina 2 (puesto 3) y Esteban Ruiz y Laura Díaz 0 (puesto 4).

Listado 9. Ranking con RANK() OVER.
SELECT
    veterinario,
    total_consultas,
    RANK() OVER (ORDER BY total_consultas DESC) AS ranking
FROM (
    SELECT
        CONCAT(v.nombre, ' ', v.apellido) AS veterinario,
        COUNT(c.id_consulta)              AS total_consultas
    FROM veterinario v
    LEFT JOIN consulta c ON c.id_veterinario = v.id_veterinario
    GROUP BY v.id_veterinario, v.nombre, v.apellido
) AS resumen
ORDER BY ranking;

También se incluyen búsquedas con LIKE, subconsultas con NOT EXISTS para detectar mascotas sin consultas, una subconsulta con MAX para identificar al veterinario con más atenciones y consultas sobre las cinco vistas.

def crear_propietario_con_mascota(
    nombre: str,
    apellido: str,
    dni: str,
    telefono: str,
    email: str,
    direccion: str,
    mascota_nombre: str,
    fecha_nacimiento: date,
    sexo: str,
    raza_nombre: str = "Mestizo",
) -> tuple[Propietario, Mascota]:
    """INSERT en 2 tablas relacionadas dentro de una transaccion."""
    raza = obtener_raza(raza_nombre)
    with db.atomic():
        duenio = Propietario.create(
            nombre=nombre,
            apellido=apellido,
            dni=dni,
            telefono=telefono,
            email=email,
            direccion=direccion,
        )
        mascota = Mascota.create(
            nombre=mascota_nombre,
            fecha_nacimiento=fecha_nacimiento,
            sexo=sexo,
            antecedentes_clinicos="Registro creado desde peewee.",
            id_propietario=duenio,
            id_raza=raza,
        )
    return duenio, mascota

La baja respeta el orden de las claves foráneas: primero se elimina la mascota (tabla hija) y luego el propietario (tabla padre), siempre dentro de la misma transacción. Si el propietario conserva otras mascotas, no se elimina.

Listado 13. Baja coordinada con verificación de mascotas restantes.
def eliminar_mascota_y_duenio(id_propietario: int, id_mascota: int) -> tuple[bool, bool]:
    """
    DELETE en 2 tablas relacionadas.
    Primero se elimina la mascota; si el duenio queda sin mascotas, se elimina
    tambien el duenio. Todo dentro de una transaccion.
    """
    with db.atomic():
        mascota = Mascota.get(
            (Mascota.id_mascota == id_mascota)
            & (Mascota.id_propietario == id_propietario)
        )
        mascota.delete_instance()

        quedan = (
            Mascota.select()
            .where(Mascota.id_propietario == id_propietario)
            .count()
        )
        duenio_eliminado = False
        if quedan == 0:
            Propietario.delete_by_id(id_propietario)
            duenio_eliminado = True
    return True, duenio_eliminado

7.4 Observaciones de la validación

  • ONLY_FULL_GROUP_BY: el script se ejecutó con el modo estricto completo. Todas las consultas con agregaciones incluyen en el GROUP BY las columnas no agregadas, por lo que no se producen errores de dependencia funcional.
  • CURDATE() en CHECK: MySQL rechaza las funciones no deterministas en restricciones CHECK. La validación se resolvió con triggers, que sí pueden evaluar la fecha actual.
  • Relación 1:1: la restricción UNIQUE sobre diagnostico.id_consulta impide cargar dos diagnósticos para la misma consulta; la prueba devolvió el error 1062.
  • Aislamiento: todas las pruebas se ejecutaron en una instancia temporal en el puerto 3307, sin modificar la base veterinaria_db utilizada en los TP anteriores.

9Retrospectiva y conclusiones

9.1 Logros del proyecto

  • Se modeló un dominio realista con once entidades y trece relaciones, sin redundancias.
  • Se normalizó hasta 3FN, eliminando una dependencia transitiva concreta entre mascota, raza y especie.
  • Se implementó un script SQL reproducible, con DDL, DCL, DML, vistas, triggers y transacciones.
  • Se construyó un CRUD en Python con transacciones atómicas sobre dos tablas relacionadas.

9.2 Dificultades y soluciones

DificultadSolución
MySQL no permite CURDATE() en CHECK.Se implementaron triggers BEFORE INSERT y BEFORE UPDATE con SIGNAL SQLSTATE.
El modo ONLY_FULL_GROUP_BY rechaza columnas no agregadas.Se incluyeron todas las columnas de agrupación en el GROUP BY.
La relación 1:1 podía convertirse en 1:N.Se agregó UNIQUE sobre diagnostico.id_consulta.

9.3 Aprendizajes

El trabajo permitió comprender que el diseño de una base de datos no termina en el diagrama: las decisiones de integridad, los permisos y las transacciones son parte del modelo tanto como las tablas. La experiencia de ejecutar el script en una instancia limpia y de probar los errores esperados fue especialmente valiosa, porque obligó a distinguir entre un esquema que «compila» y un esquema que realmente protege los datos.

También se verificó el valor de las vistas como contrato de lectura y como mecanismo de seguridad. El usuario de consulta pública no necesita conocer la estructura interna de las tablas: le alcanza con las cinco vistas para obtener la información que su rol requiere.

AAnexo: ejecución y checklist

A.1 Orden de ejecución

  1. Verificar que el servicio MySQL esté iniciado y que el puerto 3306 esté disponible.
  2. Ejecutar el script SQL con un usuario con permisos de creación: 
    mysql -u root -p < sql/veterinaria_integrador.sql
  3. Comprobar el conteo final de filas y la existencia de las cinco vistas.
  4. Instalar las dependencias de Python: 
    pip install -r python/requirements.txt
  5. Configurar las variables de entorno si los valores por defecto no coinciden: 
    $env:VET_USER = "root"
$env:VET_PASSWORD = "tu_contraseña"
$env:VET_DB = "veterinaria_integrador"
  6. Verificar la conexión y ejecutar la demo: 
    python python/veterinaria_crud.py --check
python python/veterinaria_crud.py --demo
  7. Para operar de forma interactiva: 
    python python/veterinaria_crud.py --menu
Advertencia sobre la ejecuciónEl script comienza con DROP DATABASE IF EXISTS veterinaria_integrador. Si se vuelve a ejecutar, se elimina y se recrea la base con los datos de prueba. No afecta a veterinaria_db, que pertenece a los TP anteriores.
